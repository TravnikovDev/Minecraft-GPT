# Decision-Making Architectures for Autonomous Agents in Real-Time Games and Robotics (layering, priorities, interruption)

Scope note: research done 2026-11-24. Primary sources read in full text: Gat, "On Three-Layer Architectures" (1998); Orkin, "Three States and a Plan: The A.I. of F.E.A.R." (GDC 2006); Humphreys, "Exploring HTN Planners through Example" (Game AI Pro); Champandard & Dunstan, "The Behavior Tree Starter Kit" (Game AI Pro); Graham, "An Introduction to Utility Theory" (Game AI Pro); Unreal Engine BT overview docs. Other items (BehaviorTree.CPP issues, LLM+BT papers, Guerrilla HTN, Voyager, Mindcraft) are from search-result summaries and abstracts, not full-text reads; they are flagged where it matters. Brooks' 1986 subsumption paper was not read directly; its description below comes from Gat's chapter.

## 1. Layered / hybrid architectures (three-layer, subsumption) and inter-layer communication

### Takeaway
The robotics consensus since the early 1990s is a three-layer split by *time scale and kind of state*: a stateless, bounded-time reactive controller; a sequencer that holds memory of the past and switches/parameterises controller behaviors; and a deliberator for slow, future-predicting computation that is consulted asynchronously so that "several Behavior transitions" can happen while it thinks. Subsumption is the purely reactive alternative that composes layers only by overriding signals, which works well for low-level survival behaviours but has no architectural support for goals or plans.

### Cited Findings
- Gat groups algorithms by the state they hold: stateless sensor-based algorithms go in the controller, algorithms with "memory about the past" in the sequencer, and those that "make predictions about the future" in the deliberator. — [Gat 1998, On Three-Layer Architectures](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- Names differ by system: in 3T the layers are the skill layer, sequencing layer and planning layer; in ATLANTIS they are controller, sequencer and deliberator. 3T's sequencer is based on Firby's RAPs; Gat's sequencer evolved into the ESL language. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- **Controller constraints (Gat):** (1) one iteration of the transfer function should have constant-bounded time and space; (2) it should "fail cognizantly", meaning it is designed to *detect* failure rather than try never to fail, so the sequencer and deliberator can recover; (3) avoid internal state, and any state used beyond filtering should be ephemeral and expire after a bounded time; (4) behaviours should be continuous with respect to internal state, and the sequencer manages transitions between regimes. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- The controller holds a library of "primitive behaviors or skills" (e.g. wall-following, move to destination while avoiding collisions), and which ones are active is set by an external input, i.e. by the sequencer. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- **Sequencer:** selects which primitive behaviour runs and supplies its parameters. A linear sequence of primitives is unreliable, so the sequencer must respond conditionally ("conditional sequencing", modelled on human instruction-following). It should not do computations that take long relative to the rate of environmental change, which "usually ... implies that the sequencer should not perform any search or temporal projection." — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- **Deliberator:** the place for time-consuming computation (planning, exponential search, expensive perception). Its key feature is that several behaviour transitions can occur between invoking it and getting a result. It runs as separate thread(s) and has no architectural constraints. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- **Two ways the deliberator talks to the system:** it produces whole plans for the sequencer to execute (3T/RAPs), or it answers specific queries from the sequencer (ATLANTIS/ESL). These are not mutually exclusive: RAPs can call "RAP-experts" at runtime, and ATLANTIS can ask for a full plan. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- Gat's rationale: classic sense-plan-act (SPA) fails when its internal state (world model, plan, the program counter of plan execution) "loses sync" with reality. Purely reactive systems avoid state but then depend on unreliable sensors. Layering puts each kind of state where its staleness can be managed. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- "Fast" and "slow" are relative to the environment's rate of change. Empirically, planners are not fast enough to run inside the controller in realistic environments. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- **Subsumption (as described by Gat):** layers are networks of small finite state machines joined by "wires". The only composition mechanism is overriding the contents of one wire with another, called suppression (at an input) or inhibition (at an output). It rejects plans and symbolic representations. It also advocates layering progressively more complex behaviours, but provides "no architectural mechanism" to enforce that. It had early success in fast collision-free navigation. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- In contrast to subsumption, layered architectures like T/R-III have higher layers give "input or advice" to lower ones rather than suppress them, so the layers are abstractions as well as functionality. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- Secondary summaries confirm the same three-component structure (reactive feedback control, slow deliberative planner, connecting sequencer). — [Wikipedia: Three-layer architecture](https://en.wikipedia.org/wiki/Three-layer_architecture); [Wikipedia: ATLANTIS architecture](https://en.wikipedia.org/wiki/ATLANTIS_architecture)

### Inferences
- Mapping to a Minecraft bot: **controller** = mineflayer physics plus plugins such as pathfinder, pvp, auto-eat and armor-manager, along with tick-rate reflexes (MLG water, leave lava, surface when drowning, block/strafe), each bounded in time and per physics tick (Minecraft runs 20 ticks/s, which is general game knowledge, not from the sources above). **Sequencer** = an executor that runs skills/BT/HTN plans, holds the goal stack, and reacts to events in tens to hundreds of ms without search. **Deliberator** = the LLM plus any symbolic planner (crafting-recipe search, base planning), called asynchronously, with results that can arrive after several skill transitions.
- Gat's "cognizant failure" rule maps directly onto skills that return explicit failure reasons (no path, item missing, timeout, interrupted) instead of hanging or silently doing nothing.
- Gat's rule that ephemeral state should expire after bounded time is a direct design rule for perception caches, e.g. "last seen hostile at X" must expire.
- Survival reflexes fit subsumption-style suppression well: a higher-priority reflex overrides the movement and attack outputs of whatever the sequencer is doing. Goals and plans should still live in the sequencer and deliberator, not in the reflex layer.

### Gaps
- Gat gives no concrete frequencies in Hz for each layer. Frequencies are environment-relative by design. No source was found giving canonical numbers for game bots.
- Brooks' original 1986 paper was not read directly. Subsumption details come from Gat's description.

## 2. Game AI decision patterns: FSM/HFSM, behavior trees, GOAP, HTN, utility, blackboards, and combinations

### Takeaway
Shipped games tend to use a planner or selector for *what to do*, with a small state machine or task executor for *how to do it*. F.E.A.R. used a 3-state FSM driven by a STRIPS-like GOAP planner. HTN replaced GOAP at High Moon for speed and is used by Guerrilla (Killzone 2, Horizon). Behavior trees, starting with Halo 2, give reactive priority selection via active selectors, monitors and event-driven aborts. Utility AI with priority "buckets" handles needs-based arbitration, as in The Sims. The choice is about authoring control and reactivity versus emergent problem solving.

### Cited Findings
**FSM + GOAP (F.E.A.R.)**
- F.E.A.R.'s character FSM has only three states: Goto, Animate, UseSmartObject. A* plans action sequences as well as paths. — [Orkin, GDC 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- The motivation was that the combination and interaction of all behaviours in FSMs becomes unmanageable. "FSMs are procedural, while planning is declarative." — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Each AI has a Goal Set (goals compete for activation and the planner tries to satisfy the highest-priority goal) and an Action Set. The same goals with different action sets produce different behaviour. A rat with no attack actions fails to plan KillEnemy and "falls back to the lower priority Patrol goal." — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Stated benefits: (1) goals are decoupled from actions; (2) behaviours are layered by adding goals and actions without hand-written transitions; (3) dynamic problem solving by re-planning, e.g. door held shut, then kick door, then dive through window. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- In the predecessor (NOLF2), each goal embedded its own FSM and goals were black boxes that shared no information, which caused bugs such as the Death goal not knowing the AI was sitting. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- How GOAP differs from STRIPS: (1) a cost per action, with A* finding the cheapest plan; (2) no add/delete lists; preconditions and effects use a fixed-size world-state array of 4-byte values; (3) procedural preconditions, e.g. a path-existence check that is too expensive to keep in world state; (4) procedural effects, where ActivateAction() puts the FSM into a state with parameters, because effects are not instantaneous. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Squad layer: a global coordinator periodically clusters AIs into squads. Squad behaviours send *orders*, and each AI has goals to respond to orders, so "fleeing from danger may trump following an order to advance". The squad behaviour monitors progress each tick and fails if members are interrupted. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Orkin suggests HTN for squad-level planning because it handles parallel actions better than STRIPS. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)

**HTN**
- HTN planners, unlike behavior trees, "can reason about the effects of possible actions." The example system is the one shipped in Transformers: Fall of Cybertron, a total-order forward-decomposition planner. — [Humphreys, Game AI Pro ch. 12](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- The planner uses depth-first decomposition with no cost or heuristic, and the method hierarchy culls large parts of the search. This made it "considerably faster" than the GOAP system in Transformers: War for Cybertron. — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- Guerrilla Games: Killzone 2 used HTN planning for NPCs (Remco Straatman, quoted 2009). Horizon Zero Dawn's decision-making runs on an HTN planner in the Decima engine, and Guerrilla gave a 2024 talk, "HTN Planning in Decima". These details come from search summaries; the pages were not read in full. — [Guerrilla: HTN Planning in Decima](https://guerrilla-games.com/read/htn-planning-in-decima); [Guerrilla: The AI of Horizon Zero Dawn](https://www.guerrilla-games.com/read/the-ai-of-horizon-zero-dawn); [Game Developer: Behind the AI of HZD](https://gamedeveloper.com/design/behind-the-ai-of-horizon-zero-dawn-part-1-); [GameSpot: The Future of AI in Games](https://www.gamespot.com/articles/the-future-of-ai-in-games/1100-6283722/%253C%2525=/)

**Behavior trees**
- BTs have become diverse, "from the original implementation in Halo 2 [Isla 05]" to Bulletstorm's event-driven version. — [Champandard & Dunstan, BT Starter Kit, Game AI Pro ch. 6](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- Behaviours have onInitialize / update / onTerminate(status) hooks. Statuses include RUNNING, SUCCESS and FAILURE, an ABORTED status for terminated behaviours, and SUSPENDED as "an essential part of an event-driven BT." — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- Conditions have two modes: a one-shot check, and a "monitoring mode" that keeps checking over time. — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- **Monitor** = a parallel node with a read-only condition subtree and an action subtree. The action aborts when its assumptions become invalid; the authors call this "arguably" the most useful parallel pattern. — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- **Active selector** rechecks higher-priority children regularly and aborts the running lower-priority child, e.g. "attacking a visible enemy" interrupts searching or patrolling. — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- Robotics framing: BTs are motivated by the "need for reactiveness and modularity" compared with FSMs. The book includes formal analysis of safety, robustness and efficiency. — [Colledanchise & Ögren, Behavior Trees in Robotics and AI (arXiv:1709.00084)](https://arxiv.org/abs/1709.00084); survey: [Iovino et al., arXiv:2005.05842](https://arxiv.org/abs/2005.05842)
- Unreal Engine BTs are event-driven: the tree "passively listens" for events instead of checking every frame. Conditions are decorators on composites rather than leaf tasks. Decorators with **Observer Aborts** (Self / Lower Priority) abort running work when a blackboard value changes. Services run periodic updates (e.g. pick the best target) while their subtree is active. "Simple Parallel" means "while doing A, do B as well". — [Unreal Engine BT Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview)

**Utility AI**
- Utility systems score every possible action at once and pick among the top scorers. Scores are normalised to 0-1 so they combine easily (average, multiply, min/max, weights), and each decision factor stays isolated. — [Graham, Game AI Pro ch. 9](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter09_An_Introduction_to_Utility_Theory.pdf)
- Response curves (linear, quadratic, logistic, piecewise-linear) map raw inputs to utility. The Sims' Hunger is the worked example for designer-tuned piecewise curves. The curve-design approach is credited to Dave Mark [Mark 09]. — [Graham](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter09_An_Introduction_to_Utility_Theory.pdf)
- Selection policies: always picking the best can feel robotic, and pure weighted random sometimes picks something "utterly stupid". The compromise is weighted random among the top-N or within about 10% of the best. — [Graham](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter09_An_Introduction_to_Utility_Theory.pdf)
- **Bucketing / dual utility [Dill 11]:** actions are grouped into prioritised buckets, and higher buckets are always processed first. A guard under fire never scores idle actions. In The Sims, a starving Sim only considers actions in the Hunger bucket, and falls to the next bucket only if none are valid. — [Graham](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter09_An_Introduction_to_Utility_Theory.pdf)
- Infinite Axis Utility System (Dave Mark): any number of 0-1 "considerations" per action, each through a response curve, combined into a score. New considerations can be added without affecting existing ones. This comes from secondary sources only; Mark's GDC slides were not found. — [ECS-R3 utility AI plugin docs](https://ecsrx.gitbook.io/ecsr3/ecs-r3/plugins/utility-ai-plugin); [GameAI.com: Response Curve](https://www.gameai.com/manuals/index.php/Response_Curve)

**Blackboard / shared working memory**
- F.E.A.R. decoupling forced goals and actions to share information through an "external working space", a shared working memory. Failures such as a blocked door are recorded there and taken into account when re-planning. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Unreal BTs use a Blackboard asset of keys as decision data. Decorator aborts are triggered by blackboard changes. — [Unreal BT Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview)

### Inferences
- Trade-off summary, synthesised from the sources above:
  - FSM/HFSM: simple, but transitions explode as behaviours grow (the Orkin/NOLF2 experience). Use them only for tiny "how" layers.
  - BT: authored, debuggable priority selection with clean interruption. It cannot reason about action effects (Humphreys).
  - GOAP: emergent chaining from preconditions and effects. It costs A* search and makes plans harder for designers to predict.
  - HTN: authored decomposition with effect reasoning, and faster than GOAP in practice (High Moon).
  - Utility: smooth needs-based arbitration. It needs buckets and inertia to avoid both starvation and dithering.
- For Minecraft, tech-tree progression (wood, stone, iron, diamond, with crafting dependencies) is a natural fit for HTN-style decomposition or GOAP-style backward chaining over recipes. Survival arbitration (eat, flee, fight, sleep) fits utility with buckets. Reflex interruption fits a BT active selector or an event-driven decorator abort.
- A credible combination: a top-level priority selector or utility bucket chooser, where the survival bucket always outranks the owner-command bucket, which outranks the autonomous-goal bucket. Each bucket's chosen goal runs as an HTN/GOAP plan or BT subtree, and the leaves are bounded skills.

### Gaps
- Damián Isla's Halo 2 BT paper and Dave Mark's GDC IAUS talk were not read directly.
- No primary source was retrieved on Killzone 2 HTN internals or Horizon's use of HTN with other systems.

## 3. Goal management: stacks/queues, priority arbitration, preemption, suspension/resumption, cancellation

### Takeaway
Shipped systems arbitrate by *re-evaluating priority on events* and aborting lower-priority work, with explicit termination hooks for cleanup. Typical mechanisms are GOAP goal-set priorities, BT active selectors and observer aborts, HTN method-order priority with a "method traversal record", and utility buckets plus inertia. Resumption is usually *replanning from the current world state*, not restoring a saved program counter. Owner orders are modelled as goals that compete with survival goals, not as commands that bypass arbitration.

### Cited Findings
- F.E.A.R.: goals compete for activation, and the highest-priority goal that can be planned wins. Orders from the squad layer become goals the AI weighs against others, and fleeing can trump an order. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- **HTN replanning triggers:** the plan finishes or fails, there is no plan, or "the NPC's world state changes via a sensor". — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- **HTN plan runner:** executes primitive operators in sequence and applies each task's effects on success. An operator failure fails the plan and forces a replan. The plan also fails if the current or any *remaining* task's conditions become invalid, checked against a simulated working world state. — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- **HTN priority preemption:** method order in compound tasks defines priority. To abort a running plan only for a *higher-priority* one, the planner records the method indexes chosen (a method traversal record) and accepts a new plan only if its choices are equal or higher priority. Pitfall: replanning on *every* world-state change, including changes caused by the bot's own task effects, made a lower-priority recovery get wrongly interrupted. The fix has to distinguish sensor-driven changes. — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- **HTN partial plans:** don't plan too far ahead in a changing world. Split long plans so later parts are planned when reached. Humphreys notes the difficulty of "how to continue where the partial plan left off". — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- **HTN "expected effects":** effects applied only during planning, to chain tasks whose results are set by sensors rather than by the task itself (e.g. regaining line of sight). — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- **BT interruption, two schools:** (a) non-interruptible behaviours, where abort() is a request honoured on the next update; this suits low-level animation. (b) Immediate termination with an onTerminate(ABORTED) cleanup hook; this suits high-level BTs and is the BTSK choice. Branch switches are instant, and transitions are handled elsewhere. — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- When a parallel node terminates early, all other running children must be aborted in onTerminate(). — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- BehaviorTree.CPP: running async nodes can be *halted* but not preempted, and a maintainer argues reactive nodes cover the use case. ReactiveSequence allows only one async child. A previously RUNNING child is halted only *after* another child starts, which briefly leaves two running and has caused races when cancelling ROS actions. A reactive fallback halts all non-running branches, which cancelled a long task. These come from search summaries of GitHub issues and docs. — [BT.CPP #106](https://www.github.com/BehaviorTree/BehaviorTree.CPP/issues/106); [ReactiveSequence API](https://docs.ros.org/en/api/behaviortree_cpp/html/classBT_1_1ReactiveSequence.html); [BT.CPP #1031](https://github.com/BehaviorTree/BehaviorTree.CPP/issues/1031); [Discussion #1010](https://github.com/BehaviorTree/BehaviorTree.CPP/discussions/1010)
- **Utility inertia:** re-deciding every frame causes oscillation, e.g. attack and flee both scoring 0.5. Fixes are a bonus weight for the current action ("remain committed until something truly better") or cooldowns after a decision. — [Graham](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter09_An_Introduction_to_Utility_Theory.pdf)
- Mindcraft, an LLM Minecraft bot on mineflayer, exposes `!stop` ("Force stop all actions and commands") and toggleable "modes" (self_preservation, self_defense, cowardice, unstuck, hunting, item_collecting). Their semantics were not confirmed from the source code. — [Mindcraft README](https://raw.githubusercontent.com/mindcraft-bots/mindcraft/develop/README.md); [Mindcraft repo](https://github.com/kolbytn/mindcraft)

### Inferences
- Recommended arbitration ladder for this bot: (1) reflexes (falling, lava, drowning, imminent damage), which preempt instantly and are never queued; (2) owner commands; (3) maintenance needs (eat, repair, retreat at night); (4) self-chosen progression goals. Owner commands are high priority but still lose to reflexes, mirroring F.E.A.R.'s "fleeing may trump an order". Utility buckets are a well-sourced way to express this.
- Suspension and resumption: rather than saving a skill's internal progress, push the interrupted *goal* (not the plan) back on a goal stack and **replan on resume** from current world state. This follows HTN/GOAP practice and Gat's warning that stored plan state goes stale.
- Cancellation: every async skill should accept a cancellation signal and run idempotent cleanup (stop pathfinder, clear control states, release keys) like BTSK's onTerminate(ABORTED). The BT.CPP race (new child started before old one halted) suggests: await the old skill's halt before starting the new one, or make halting synchronous. In JS terms this would be an AbortController/AbortSignal per task. That is a standard web/Node API, but no game-AI source using it was found, so this is inference.
- Add commitment and hysteresis (Graham's inertia) to autonomous-goal selection so the bot doesn't flip between "mine iron" and "gather wood" every evaluation.
- Pitfall to copy from Humphreys: don't let the bot's own actions' world-state changes trigger priority re-evaluation that interrupts itself. Tag events by source (self vs external).

### Gaps
- No academic source was found specifically on cancellation-token patterns in game AI. The AbortSignal suggestion is engineering inference.
- No published guidance was found on fairness/starvation between owner commands and autonomous goals beyond priority buckets.

## 4. Perception and world-state abstraction (sensors, beliefs, staleness, symbolic state)

### Takeaway
Shipped planners do not plan over raw game state. Time-sliced sensors encode raw observations into a small, *abstract*, enum/boolean world-state vector that contains only what decisions need. Expensive facts are computed lazily via procedural preconditions, and learned facts (e.g. "door is blocked") go into shared working memory. Robotics adds the rule that stored state must expire.

### Cited Findings
- HTN world state is "essentially a vector of properties" (an array indexed by enum). It "only needs to represent what is needed for the HTN to make decisions", e.g. WsEnemyRange as abstract ranges, not distance. — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- Recommended: "a set of time-sliced sensors" (vision, hearing, range, health), each owning some world-state properties and encoding its information into planner-readable form. World state is updated by sensors *and* by completed task effects. — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- F.E.A.R. world state is a fixed-size array of 4-byte values. Facts too expensive to keep there, such as whether a safe path exists, are checked procedurally only when the planner needs them. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- F.E.A.R. AI sensors keep an up-to-date list of potentially valid cover positions nearby, which the squad layer consumes, so higher layers don't re-analyse the map. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Gat: SPA failures come from internal state losing sync with the world. Abstraction isolates aspects of reality that "can be tracked or predicted reliably". Controller-level state should be ephemeral with bounded expiry. Sometimes remembering a wall that sensors no longer report is correct. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- Unreal BT: a blackboard of keys holds decision data, and services refresh values periodically while a subtree is active. — [Unreal BT Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview)

### Inferences
- Suggested layering for the bot: **raw state** (mineflayer `bot.entity`, `bot.entities`, world chunks, inventory events) feeds **sensors**, which are event-driven where mineflayer emits events (health, entityHurt, physicsTick) and time-sliced otherwise (nearest hostile scan, nearby resources). Sensors write **beliefs**, each with value, timestamp, source and TTL (e.g. `hostileNear: {entityId, dist bucket, seenAt}`). A **symbolic world-state** projection is derived from beliefs (hasPickaxeTier, foodLevelBucket, inDanger, isNight, ownerNearby) for planners and the LLM.
- Distinguish **facts** the bot observed directly and that stay true until invalidated (inventory counts, known chest contents with a timestamp) from **observations** that decay (mob positions). Gat's bounded expiry rule covers the latter.
- Feed the LLM the compact symbolic projection, not raw entity dumps. This bounds tokens and matches the "only what decisions need" principle.

### Gaps
- No source was found giving concrete sensor update rates for game NPCs. "Time-sliced" is stated without numbers.

## 5. Skills/actions as composable units (preconditions/effects, status, retries, idempotency)

### Takeaway
The common model is STRIPS-like: actions or primitive tasks have symbolic preconditions and effects for planning, plus procedural checks and a runtime operator that returns RUNNING/SUCCESS/FAILURE (with ABORTED/SUSPENDED in event-driven BTs). Robustness comes from cognizant failure detection, re-validating remaining preconditions during execution, recording failure knowledge in memory, and replanning rather than blind retry.

### Cited Findings
- STRIPS actions are defined by preconditions and effects; an action may execute only if all preconditions are met. GOAP adds per-action cost, procedural preconditions, and procedural effects (activation sets an FSM state and parameters, since effects aren't instantaneous). — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Adding a precondition to one shared action changes every plan that uses it. Orkin's example adds a TurnOnLights action and a LightsOn precondition on Goto. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- HTN primitive task = operator + conditions + effects. Compound tasks have ordered methods with conditions. The plan runner re-validates remaining tasks' conditions during execution and replans on failure. — [Humphreys](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter12_Exploring_HTN_Planners_through_Example.pdf)
- BT behaviour lifecycle: onInitialize, update returning status, onTerminate(status). Completion statuses report whether the behaviour achieved its purpose. — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- Controller algorithms should be designed to "never fail to detect a failure" so upper layers can recover. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)
- Re-planning with failure knowledge recorded in working memory produces adaptive behaviour (the door example). — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Voyager (Minecraft, GPT-4) stores successful *executable code skills* in a library indexed by description embeddings and refines them via iterative prompting with environment feedback, execution errors and self-verification. Its automatic curriculum is generated by GPT-4. It reports 3.1x more unique items and up to 15.3x faster tech-tree milestones than prior state of the art. — [Voyager, arXiv:2305.16291](https://arxiv.org/abs/2305.16291); [NeurIPS 2023 listing](https://neurips.cc/virtual/2023/79179)

### Inferences
- Skill contract for this bot: a declarative descriptor (name, symbolic preconditions/effects, rough cost, interruptibility class) plus an async run that accepts a cancel signal and returns a typed result: success, failure with reason enum, or aborted. Preconditions should be checked at start *and* the planner/sequencer should re-check them as world state changes (HTN runner style).
- Idempotency: write skills as "ensure X" (ensureHasItem, ensureAt, ensureEquipped) that check the current state first and are no-ops if already satisfied. Retrying after a partial failure is then safe even though the world changed underneath. (The repo already has `ensure*.ts` files, which fits this.) This inference rests on the HTN/GOAP precondition model.
- Retry policy: bounded retries for transient failures (path blocked, mob in the way), then record the failure as a fact with a TTL (e.g. "tree at X unreachable") and replan. Don't loop, which follows Orkin's working-memory pattern. Mindcraft and Voyager-style LLM code generation is a deliberative-layer tool; generated code should run as a cancellable skill, not as the reflex layer.

### Gaps
- No primary game-AI source was found that explicitly discusses "idempotency" by that name. The ensure-style recommendation is inference.

## 6. Where an LLM fits (cost/latency)

### Takeaway
Published LLM+game/robot work consistently puts the LLM in the **deliberative layer**: intent parsing, task decomposition, curriculum, writing or generating BTs and skills. Fast reactive execution goes to BTs, scripted skills or small policies, explicitly because LLM inference latency is too high for in-loop control. This matches Gat's rule that slow computation must not sit in the sequencer or controller.

### Cited Findings
- "Agents Play Thousands of 3D Video Games" (arXiv 2503.13356, 2025): an LLM generates behavior trees in a DSL, executed by rule-based nodes plus neural components. The authors frame this as letting LLM-generated policies run in real time without typical LLM-agent latency. This is from the abstract and search summary. — [arXiv:2503.13356](https://arxiv.org/html/2503.13356v1)
- Hierarchical language agent for Overcooked (arXiv 2312.15224): a slow LLM for intention reasoning, a lightweight fast LLM for macro actions, and a reactive policy for atomic actions, explicitly targeting high LLM inference latency in real-time collaboration. This is from the abstract and search summary. — [arXiv:2312.15224](https://arxiv.org/abs/2312.15224v2)
- HIVE (arXiv 2412.11761): the LLM plans for RTS units, and each unit runs a behavior tree on local observations at every step. The paper names LLM inference overhead as a key limitation. — [arXiv:2412.11761](https://arxiv.org/html/2412.11761v1)
- Dendron (arXiv 2404.07439): behavior trees as a structured programming layer for LLM agents. — [arXiv:2404.07439](https://arxiv.org/html/2404.07439)
- A robotics paper (arXiv 2508.09621, 2025) uses BTs as the reactive control layer for LLM-interpreted commands and reports success, latency and robustness. It was not read in full. — [arXiv:2508.09621](https://arxiv.org/pdf/2508.09621v1)
- Voyager (Minecraft): the LLM is used as a black box via prompting with no gradient updates. It writes code skills and proposes curriculum tasks, and Mineflayer executes them. — [Voyager](https://arxiv.org/abs/2305.16291)
- Mindcraft: "Mineflayer handles basic navigation and actions" so the LLM focuses on communication and reasoning. Commands like `!stop` and per-agent "modes" run outside the LLM. — [Mindcraft README](https://raw.githubusercontent.com/mindcraft-bots/mindcraft/develop/README.md); [Mindcraft paper, arXiv:2504.17950](https://arxiv.org/html/2504.17950v1)
- Gat: the sequencer must not do computations that are long relative to environmental change, and the deliberator may take long enough for several behaviour transitions. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)

### Inferences
- LLM roles, in order of value per cost: (1) natural-language intent parsing of owner chat into a validated structured goal (Zod schema), called once per message; (2) occasional high-level planning or goal selection when idle or when a plan fails irrecoverably; (3) chat responses; (4) optionally generating new skills offline, Voyager-style. Avoid putting the LLM in survival or combat loops. Mineflayer reflexes must run with zero LLM dependency.
- LLM calls should be **asynchronous queries** in Gat's ATLANTIS style. The sequencer keeps running (and reflexes keep firing) while awaiting a response, and must handle a stale answer, e.g. by re-validating the LLM's chosen goal's preconditions against current world state before adopting it.
- Latency budget reasoning (inference, not sourced): LLM round-trips typically take hundreds of milliseconds to many seconds, while Minecraft hazards (lava, falling, a creeper fuse) play out in roughly 1-2 s. So any hazard response must be local code. This is consistent with all the papers above, but no paper gave a numeric budget.

### Gaps
- No published numeric latency budget for LLM use in real-time game agents was found. The papers state the problem qualitatively.
- The Overcooked and 3D-games papers were read only via abstracts and summaries. Their specific latency figures, if any, were not verified.

## 7. Event-driven design (event buses, observers, actors, single-threaded event loop)

### Takeaway
Modern game BTs (Unreal, Bulletstorm via BTSK) are event-driven. A scheduler keeps a list of active behaviours, and observers fire on termination or blackboard change instead of the tree being traversed from root every frame. Decorator observers abort running branches when watched values change. In a single-threaded Node/Bun bot the same pattern maps onto mineflayer's event emitter plus a central scheduler, with the main risk being long synchronous work blocking reflexes.

### Cited Findings
- Event-driven BTs keep active behaviours in a scheduler list instead of traversing from root each frame. There are two variants: (a) re-traverse the whole tree when active behaviours terminate *or the world/blackboard changes*, "in a similar way than a planner would"; (b) incrementally update via parents. — [BTSK §6.4.4](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- A **behavior observer** is a callback fired by the scheduler when a behaviour terminates. Composites ask the scheduler to run children and register observers rather than ticking them directly. — [BTSK](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter06_The_Behavior_Tree_Starter_Kit.pdf)
- Unreal: the tree "passively listens" for events. Only changes in execution location or blackboard values appear in debug history. Observer-abort decorators replace constantly-checking parallel conditions. — [Unreal BT Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview)
- F.E.A.R.'s squad layer communicates via orders that individual agents treat as goals, with per-tick progress monitoring. This is a message-passing pattern between layers. — [Orkin 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)
- Gat's deliberator runs as separate threads, and the sequencer queries it, so the reactive loop never waits on deliberation. — [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)

### Inferences
- In Bun/Node there are no threads by default, so Gat's "separate thread" for the deliberator becomes "un-awaited async I/O". LLM HTTP calls are naturally non-blocking. The real constraint is *CPU-bound* synchronous work (large pathfinding searches, big world scans, synchronous HTN/GOAP search) on the event loop, which delays physicsTick handlers. Keep such work time-sliced (yield between chunks) or bounded. Worker threads exist in Node/Bun but are inference here, not sourced.
- A lightweight internal event bus (typed events such as `danger.lava`, `owner.command`, `skill.finished`, `belief.changed`) with a single **arbiter/scheduler** that owns "what is running now" gives the BTSK scheduler pattern. Only the arbiter starts and cancels skills, which avoids the two-concurrent-skills race seen in BT.CPP.
- Actor-model framing (each layer as an actor with a mailbox) is compatible but not required in a single process. No game-AI source was found that recommends actors specifically for single-character bots.
- Avoid both extremes: pure polling every physics tick wastes CPU on deliberative checks, and pure events miss continuous conditions (e.g. slowly falling health). Combine events for discrete changes with Unreal-style periodic "services" for continuous ones.

### Gaps
- No authoritative source was found on actor-model or event-bus architectures specifically for game bots. The recommendations above are engineering inferences from BT scheduler and observer patterns.
- No source was found that measures Node/Bun event-loop latency effects on mineflayer reflexes.
